## 1. 목표와 기준

### 1.1 오늘의 목표

오늘은 실제 로봇과 Jetson이 있는 작업 환경에서 다음 흐름을 한 번에 연결한다.

```text
ESP32 안전 제어·엔코더
→ Jetson ROS 2 LiDAR·odometry·TF
→ 수동 주행 SLAM 지도 생성
→ Jetson 로컬 고정 경로 주행
→ 장애물 정지·해제 후 재개
→ MQTT pose/status 및 프론트 지도 관제
→ AI 차량 탐지 + 같은 방향의 LiDAR 거리
→ 차량 map 좌표 계산
→ 백엔드 차량 판별 API
```

### 1.2 확정 결정

| 항목 | 결정 |
|---|---|
| 지도 생성 | 첫 지도는 사람이 로봇을 조종하며 SLAM으로 생성한다. 자동 미지영역 탐색은 후순위다. |
| 순찰 경로 | 백엔드 경로 API를 기다리지 않고 Jetson 로컬 `route.yaml`을 사용한다. |
| 주행 방식 | 저장된 지도에서 순서가 고정된 waypoint를 따라 저속 주행한다. |
| 장애물 | 우회하지 않고 정지하며, 장애물이 사라지면 남은 경로를 재개한다. |
| 차량 위치 | 카메라 bbox 중심 방향과 같은 방향의 2D LiDAR 거리를 결합하는 단순 방식을 먼저 사용한다. |
| 불법주차 판정 | 로봇은 차량의 `map x,y`와 번호판을 보내고, 백엔드가 기존 `PARKING` 구역과 비교한다. |
| AI 코드 | 실제 AI 코드가 존재하는 작업 환경을 기준으로 연결한다. GitLab 모델 파일만으로 런타임을 재구성한다고 가정하지 않는다. |
| 구역 API | 불법주차 판정만을 위해서는 당일 필수가 아니다. 로봇의 구역별 로컬 행동이 필요할 때 백엔드에 요청한다. |

## 4. Codex 작업 계획

Codex는 실제 장비가 있는 컴퓨터와 Jetson에 접근한 뒤 아래 순서로 작업한다. 각 단계의 게이트가 실패하면 다음 단계로 넘어가지 않는다.

### C0. 실제 상태 보존과 기준 확정

1. PC Git 작업 트리, GitLab 원격 브랜치, Jetson 로컬 소스와 실행 서비스를 읽기 전용으로 확인한다.
2. Jetson에만 존재하는 AI 코드와 설정을 백업 대상으로 식별한다.
3. 비밀값, 모델 대용량 파일, 캘리브레이션 로컬값이 커밋되지 않도록 경로를 분리한다.
4. 구현 브랜치는 실제 최신 IoT 브랜치에서 새로 만든다. `iot/dev`, `develop`에 직접 push하지 않는다.

**완료 게이트**: 어떤 파일과 서비스가 실제 진실원천인지 설명할 수 있고 기존 변경을 덮어쓰지 않는다.

### C1. 안전 preflight와 측정 보조 도구

다음 도구를 현재 ESP32 JSON 시리얼 계약에 맞춰 준비한다.

| 도구 | 역할 | 자동 계산 | 사용자 입력 |
|---|---|---|---|
| `integration_preflight.py` | 시리얼, STOP, HELLO, 엔코더, LiDAR, 카메라, ROS, MQTT, 백엔드 상태를 한 번에 점검 | 성공/실패와 장치 경로 리포트 | 움직임 승인 |
| `calibrate_encoder_ticks.py` | 바퀴를 손으로 정해진 횟수 회전시키기 전후 tick 차이를 기록 | 바퀴 1회전당 tick의 반복 중앙값 | 실제 회전 횟수 |
| `calibrate_drive_distance.py` | 제한된 PWM으로 짧게 직진하고 엔코더 변화 기록 | 유효 tick/m, 좌우 편차 | 실제 이동 거리 측정 |
| `calibrate_steering.py` | STOP 상태에서 중앙·좌·우 조향을 단계별 명령 | 명령별 기록과 안전 범위 | 실제 바퀴 각도 또는 회전반경 |
| `lidar_camera_alignment_probe.py` | 카메라 중심선과 LiDAR 각도별 거리를 동시에 표시 | 정면 각도 오프셋과 유효 거리 창 후보 | 표적 배치와 실제 거리 |

안전 원칙:

- 기본 실행은 모터를 움직이지 않는다.
- 실제 구동은 명시적인 옵션과 사용자 승인 없이는 수행하지 않는다.
- 조향·모터 시험 전 ESP32 STOP과 바퀴 공중 부양을 확인한다.
- 생성된 실제 보정값은 우선 로컬 전용 설정에 쓰고, 검토 후 예시값만 Git에 반영한다.

**완료 게이트**: 엔코더 tick/m, 휠베이스, 조향 중앙·안전 범위, LiDAR 정면 방향을 수치로 확보한다.

### C2. ROS 2 기반 주행 좌표계

1. YDLIDAR 드라이버와 `/scan` 주기·방향·유효 범위를 검증한다.
2. 엔코더와 조향 명령을 사용하는 자동차형 2D odometry를 구성한다.
3. 최소 TF를 연결한다.

```text
map -> odom -> base_link -> laser_frame
                      \-> camera_frame
```

4. RViz에서 로봇을 직진·곡선 이동시켜 TF와 scan이 차체와 함께 움직이는지 확인한다.

**완료 게이트**: TF 오류가 없고, 실제 전진 시 odom x가 증가하며, 조향 시 yaw가 기대 방향으로 변한다.

### C3. SLAM 지도 생성과 업로드

1. `slam_toolbox` 비동기 mapping 설정과 launch를 추가한다.
2. 저속 수동 조종으로 시연 공간의 외곽과 내부 특징을 통과한다.
3. 출발 위치 부근으로 돌아와 지도 폐곡합을 확인한다.
4. PGM/PNG, YAML, pose graph를 로컬에 저장한다.
5. 현재 백엔드 계약에 맞춰 PNG, resolution, origin을 업로드한다.
6. 프론트에서 지도와 구역 편집 화면을 확인한다.

**완료 게이트**: 저장한 지도를 다시 로드할 수 있고 프론트에서 같은 지도가 보인다.

### C4. Jetson 로컬 고정 경로

지도 생성 뒤 RViz에서 좌표를 선택해 다음 형식의 로컬 파일을 만든다.

```yaml
schema_version: 1
map_id: 7
map_version: 1
route_id: demo-loop-v1
waypoints:
  - sequence: 1
    x: 0.50
    y: 0.80
    yaw_deg: 0.0
    action: PASS
  - sequence: 2
    x: 2.00
    y: 1.20
    yaw_deg: 0.0
    action: SCAN
  - sequence: 3
    x: 0.80
    y: 0.60
    yaw_deg: 180.0
    action: DESTINATION
```

1. waypoint 한 개부터 저속으로 검증한다.
2. 2~3개를 연결한 뒤 전체 경로를 실행한다.
3. 자동차형 차체가 제자리 회전을 요구하지 않도록 waypoint와 yaw를 조정한다.
4. 경로 파일은 실제 Jetson 로컬 운영값과 Git 예제 파일을 분리한다.

**완료 게이트**: 같은 출발 위치에서 고정 경로를 한 번 완주하고 목적지에서 정지한다.

### C5. 장애물 정지·재개

1. `/scan` 정면 안전 영역에 점이 들어오면 ESP32로 즉시 STOP을 전달한다.
2. MQTT status를 `OBSTACLE_STOP`으로 전환한다.
3. 일정 시간 연속으로 안전 영역이 비었을 때 기존 경로의 남은 지점부터 재개한다.
4. 센서 단절·오래된 scan은 장애물 해제로 취급하지 않고 정지 상태를 유지한다.

**완료 게이트**: 장애물을 놓았을 때 충돌 전에 정지하고, 제거 후 새 순찰을 만들지 않고 기존 경로를 재개한다.

### C6. 백엔드·프론트 관제 연결

1. localization pose를 기존 MQTT 계약의 meter, degree 규칙으로 변환한다.
2. `pose` 1초, `status` 5초 및 상태 변경 즉시 전송을 검증한다.
3. 프론트 지도 좌표와 RViz 좌표가 같은 방향과 위치를 가리키는지 비교한다.
4. `DESTINATION` 진입 시 백엔드가 순찰 완료 및 `STOP_PATROL`을 발행하는지 확인한다.

**완료 게이트**: 실제 로봇 이동이 프론트 지도에 표시되고 목적지에서 백엔드 주도 종료가 동작한다.

### C7. 단순 카메라-LiDAR 차량 위치

복잡한 3D 투영 대신 다음 2D 계산을 먼저 구현한다.

```text
u = 차량 bbox 가로 중심 픽셀
alpha = 카메라 픽셀 u를 정면 기준 각도로 변환 + 측정한 카메라/LiDAR 각도 오프셋
r = LiDAR의 alpha 주변 유효 거리들의 중앙값

vehicle_x = robot_x + r * cos(robot_yaw + alpha)
vehicle_y = robot_y + r * sin(robot_yaw + alpha)
```

처리 규칙:

- AI는 차량 여부, bbox, confidence, track ID, 번호판 결과를 제공한다.
- Robot은 가장 가까운 시각의 `/scan`을 사용한다.
- 한 점이 아니라 작은 각도 창의 중앙값을 사용한다.
- 유효 LiDAR 점이 없거나 차량 두 대가 같은 방향에 겹치면 판정을 보류한다.
- 같은 순찰에서 같은 번호판 또는 가까운 map 좌표의 차량은 병합한다.
- Robot은 차량의 `map x,y`를 `/api/robot/vehicle-checks`에 보낸다.
- `PARKING` 포함 여부와 최종 이벤트 종류는 백엔드가 결정한다.

**완료 게이트**: 알려진 위치에 둔 차량 한 대의 추정 좌표가 지도에서 같은 구역에 들어가고 백엔드 판별 요청이 성공한다.

### C8. 재실행과 문서화

1. 실행 순서를 launch 또는 서비스 단위로 정리한다.
2. 전원 재인가 후 STOP 기본값을 검증한다.
3. 로그 위치와 점검 명령을 handoff에 기록한다.
4. 실제 변경사항을 별도 구현 브랜치에 커밋하고 테스트 결과를 남긴다.

## 6. 다른 파트에 요청할 사항

### 6.1 AI 담당

- 실제 Jetson 실행 명령과 의존성 설치 방법
- 자동차 탐지 결과의 bbox, confidence, track ID 제공
- 번호판 OCR 성공·실패 표현 방식
- 증거 이미지 저장 경로와 파일 생성 완료 시점
- 동일 차량을 여러 프레임에서 추적하는 기준

AI가 `ILLEGAL_PARKING`을 직접 확정하기보다 `CAR` 탐지 정보와 번호판을 제공하고, 최종 불법주차 여부는 현재 백엔드 차량 판별 API가 결정하도록 맞춘다.

### 6.2 백엔드 담당

당일 불법주차 판정에는 기존 `/api/robot/vehicle-checks`를 우선 사용한다. 다음은 후속 요청이다.

```http
GET /api/robot/maps/current/navigation-config
Authorization: Bearer {robotServiceToken}
```

응답 후보:

```json
{
  "map": {
    "mapId": 7,
    "version": 1,
    "frameId": "map",
    "resolution": 0.05,
    "originX": -10.0,
    "originY": -8.5,
    "originYaw": 0.0
  },
  "zones": [
    {
      "zoneId": 21,
      "name": "주차구역 A",
      "type": "PARKING",
      "startX": 2.0,
      "startY": 1.0,
      "endX": 7.0,
      "endY": 4.0
    }
  ]
}
```

용도는 불법주차 서버 판정이 아니라 로봇이 구역별 로컬 동작을 수행하고, 재시작 후 지도 버전을 검증하는 것이다.

### 6.3 프론트 담당

- 기존 지도 위 구역 지정 기능과 실제 좌표 변환을 유지한다.
- 당일에는 경로 편집 기능을 요구하지 않는다.
- 후속으로 waypoint 등록, 순서 변경, `PASS`/`SCAN`/`DESTINATION` 행동 지정 기능을 요청한다.

## 7. 당일 시간 계획과 게이트

| 경과 시간 | Codex 작업 | 사용자 작업 | 통과 조건 |
|---:|---|---|---|
| 0~1시간 | 실제 파일·서비스 보존, preflight 실행 | 전원·받침·비상정지 준비 | STOP, serial, 장치 인식 성공 |
| 1~3시간 | 보정 도구 실행, odometry·TF 구성 | 바퀴 회전·거리·휠베이스·조향 실측 | odom/TF/scan 정상 |
| 3~5시간 | SLAM 설정, 지도 저장·업로드 | 수동 맵핑 주행, 프론트 구역 지정 | 재로딩 가능한 지도 |
| 5~8시간 | localization, local route, 장애물 로직 | waypoint 선택, 저속 경로·장애물 시험 | 1회 경로 완주와 정지·재개 |
| 8~10시간 | MQTT pose/status, 목적지 종료 연결 | 프론트 관제와 종료 확인 | RViz/프론트 위치 일치 |
| 10~12시간 | AI 연결, 단순 차량 locator, REST 연동 | 차량 배치와 결과 판정 | 차량 1대 좌표·API 성공 |

시간은 선행 게이트가 첫 시도에 통과하는 경우의 목표값이다. 전기·시리얼·센서 문제가 발생하면 해당 시간을 다음 단계에서 차감하지 않고 원인을 먼저 해결한다.

## 8. 실패 시 축소 순서

| 실패 항목 | 축소 시연 |
|---|---|
| 엔코더 odometry 불안정 | 수동 맵핑과 LiDAR 위치 추정까지만 검증하고 자율 경로 주행을 중단한다. |
| Nav2 경로 추종 불안정 | 사람이 고정 경로를 조종하며 pose·관제·AI 통합을 검증한다. |
| 실제 AI 런타임 불안정 | `/ai/detections` 모의 메시지로 Robot→백엔드 경로를 먼저 검증한다. |
| 차량-LiDAR 매칭 실패 | 차량 탐지와 같은 방향 LiDAR 거리까지 화면·로그로 분리 검증하고 불법주차라고 단정하지 않는다. |
| 백엔드 구역 API 미구현 | 로봇 구역별 행동은 보류하고 차량 map 좌표를 기존 백엔드 판별 API에 보낸다. |
| 지도 업로드 실패 | 로컬 지도·경로 주행을 계속하고 multipart 요청·인증 문제를 별도 진단한다. |

## 9. 완료 기준

### 9.1 필수 완료

- [ ] 안전 preflight가 반복 실행 가능하다.
- [ ] 로봇별 보정값이 측정 근거와 함께 로컬 설정으로 저장된다.
- [ ] 수동 주행으로 지도를 만들고 재로딩할 수 있다.
- [ ] 로컬 `route.yaml`로 고정 경로를 한 번 완주한다.
- [ ] 장애물 앞에서 정지하고 제거 후 남은 경로를 재개한다.
- [ ] 실제 pose/status가 백엔드와 프론트에 표시된다.
- [ ] 전원 재인가 또는 프로세스 종료 시 모터가 기본 정지 상태다.

### 9.2 목표 완료

- [ ] 실제 AI 차량 탐지 결과를 Robot 런타임이 수신한다.
- [ ] 차량 방향의 LiDAR 거리와 robot pose로 차량 map 좌표를 계산한다.
- [ ] 차량 판별 API 한 건과 증거 이미지 업로드가 성공한다.

### 9.3 품질 기준

- [ ] 실제 보정값, 토큰, 인증서, 비밀번호가 Git에 포함되지 않는다.
- [ ] 움직임을 발생시키는 도구는 기본 비활성이고 명시적 승인 옵션을 요구한다.
- [ ] 각 게이트의 명령, 로그와 결과가 handoff에 기록된다.
- [ ] 기존 물리 주행 회귀 테스트와 새 비이동 테스트가 통과한다.
